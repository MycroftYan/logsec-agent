# 02 · 日志安全分析对话智能体：系统方案设计（v0.4 · AgentScope 底座版）

这份方案回答一个问题：四个人、8 周、每人每周 1–2 小时，怎样做出一个满足老师要求的日志安全智能体。

课程：北航网安学院本科生科研课堂
日期：2026-11-17
版本：v0.4，替换 v0.3（APT-Hunter 底座版），两版的区别见第 11 节
配套材料：`01-系统调研与对比.md`、`04-四套系统详解与评测.md`（调研依据）；`logsec-agent_v0.1.zip`（最小原型代码）；`测试数据_v1.zip`（输入数据与说明）

---

## 1. 结论

**以开源智能体框架 AgentScope 2.0 为底座，改造成一个能对话的日志安全分析智能体。框架提供现成的智能体零件，我们补上日志安全这一层。**

用户用自然语言提问，例如"这个案件里发生了什么可疑行为"。智能体自己决定查哪些日志、查几次，最后给出回答，并列出支撑结论的事件编号。

下文反复用到四个词，先说明：

- **ReAct 循环**：模型"思考 → 调用工具 → 看结果 → 再思考"反复进行，直到能回答为止。这是老师要求的智能体核心。
- **中间件**：框架在循环的各个环节留出的插入点，可以在不改循环本身的情况下加功能。
- **事件编号**：日志库里每条日志事件的唯一编号。回答必须引用它，方便核对。
- **ATT&CK 战术**：安全业界通用的攻击行为分类，按攻击者的目的分，例如"横向移动""权限提升"。

### 1.1 需求和实现怎么对应

| 老师要的 | AgentScope 现成的 | 我们改造或新增的 |
|---|---|---|
| **能对话的 ReAct 循环** | `Agent` 加终端对话入口，十几行就能聊 | 日志安全的系统提示词 |
| **工具** | `Toolkit`，普通 Python 函数包一层就是工具 | 6 个只读的日志查询工具 |
| 上下文管理 | `ContextConfig`：超阈值自动压缩历史、工具结果超长自动截断 | 调参数，做开和关的对比 |
| **记忆** | 记忆中间件（用 Markdown 文件跨会话记东西） | 规定记什么：已确认的结论、常见误报 |
| **结论可信（加分项）** | 自定义中间件 | 检查回答里引用的事件编号是否真实存在 |
| 主题是日志安全 | 无。它是通用框架，不含安全知识 | 公开攻击日志数据集、案件划分、评测题目 |

### 1.2 为什么可行

第 2 周末就满足老师的两条硬要求：主题是日志安全，有能对话的 ReAct 循环。之后每周只加一个组件，每个组件是一处配置或一个不到百行的文件。任何一周没做完，前面的成果仍然可以演示和交付。

### 1.3 人、时间、模型、数据

- **人**：4 人。下文用字母代称：A 是大四人工智能同学，只指导不动手；B 是大三网安同学；C 和 D 是两位大二计算机同学。
- **时间**：8 周。动手的 3 人每人每周 1–2 小时，合计 24–48 人时（3 人 × 8 周 × 1–2 小时）。
- **模型**：DeepSeek 的 `deepseek-flash`，按量计费。
- **数据**：全部来自公开数据集，不需要自己采集日志。

### 1.4 原型现状

最小原型已经做出来并实际跑通，范围对应排期的第 1–2 周。以下是 2026-11-17 在 macOS 上的实测结果；2026-11-18 又在 Windows 11 + Python 3.11.5 上完整复测一遍，结果见本节末尾。

| 项目 | 现状 |
|---|---|
| 日志库 | 建库脚本把两份数据导入 SQLite：6,633 条事件（主数据 4,633 条加 SSH 日志 2,000 条），250 个案件 |
| ReAct 循环 | 已跑通。终端里可以多轮对话，也可以单次提问并打印每一步的工具调用 |
| 日志工具 | 3 个基础工具已实现：列案件、搜事件、取单条事件 |
| 测试 | 9 个不调用模型的测试全部通过，其中一个逐条检查工具输出里不含标准答案 |
| 第 3–7 周的组件 | 只留了占位文件和中文说明，开关默认关闭，等同学来做 |
| 代码仓库 | <https://github.com/MycroftYan/logsec-agent>，已用 Git 管理 |

两次实测提问：

- 问"case_010 里发生了什么可疑行为"：智能体自己调用了约 10 次工具，还原出"清除安全日志 → 远程登录 → 重置机器账号密码"的过程。回答引用的事件编号都能在日志库里查到。这次提问消耗约 2 万输入 token、2 千输出 token。
- 问"SSH 日志里最活跃的攻击来源是哪个地址"：答案正确（183.62.140.253，286 次失败登录），但它调用了 32 次工具，消耗约 16 万输入 token，并且撞到了循环上限。原因是现在没有统计工具，它只能一页页翻搜索结果。第 3 周要加的统计工具就是解决这个问题的。

**Windows 复测（2026-11-18）**：用 `uv venv --python 3.11` 建环境、`uv pip install -r requirements.txt` 装依赖、`python scripts\build_db.py` 建库（events 6,633 / cases 250 / labels 250）、`python -m pytest` 9 项测试全通过（5.4 秒）。用同一个 case_010 问题提问，智能体调用 11 次工具，给出"清安全日志 → 远程 Administrator 登录 → SAMR/LSARPC 远程枚举 → 尝试重置机器账户密码 → 机器账户 Kerberos 登录"的完整链条，每条结论都带 uid；输入 27,441 / 输出 2,828 token，正常结束（未撞循环上限）。完整记录见仓库 `docs/demo-case010.md`。

## 2. 为什么选 AgentScope

### 2.1 选型理由

底座用 AgentScope 2.0.12。它由阿里开源，采用 Apache-2.0 协议，对应论文 arXiv:2402.14034。2026-11-17 核实：2.0.12 于 11 月 16 日发布，需要 Python 3.11 以上，仓库当天仍在更新。

- **零件齐全，和老师的要求一一对应**（见 1.1 的表）。同学的工作是配置和改造，不是从零写智能体。
- **零件可以单独开关**。上下文管理是一个配置对象，记忆是一个中间件，加上或去掉只改一两行。这样能直接对比"有这个组件和没这个组件差多少"，同学也能看清智能体由什么构成。
- **直接支持 DeepSeek、通义等国内模型**，不需要自己写接口适配。
- **维护活跃，文档完整**，每个零件都有独立的文档页。

### 2.2 和调研过的其他系统的关系

| 系统 | 在本方案中的角色 | 具体借鉴什么 |
|---|---|---|
| **AgentScope** | **底座**，直接使用并改造 | ReAct 循环、工具管理、上下文管理、记忆、中间件 |
| **APT-Hunter v4.0**（课程给定） | **领域设计参考** | 它的分诊智能体有 5 个工具：**列线索、搜告警、取单条事件、看时间窗、提交结论**。我们的日志工具按这个思路设计。它"结论只能提议、不能直接写入"的做法也用在证据校验里 |
| **Ariadne**（课程给定） | 设计参考 | "结论必须能回指到证据，否则不接受"的校验思路；可复现的评测方法 |
| **ZettelForge**（课程给定） | 设计对照 | 记忆应该记什么、怎么检索。它在 Windows 上无法直接运行，所以不用它的代码 |
| **Agent-Kernel**（课程给定） | 对比说明 | 面向大规模社会模拟，没有现成的对话循环，也没有安全知识，不适合当底座 |
| Wazuh-Autopilot、HESP | 对比说明 | 前者部署重，后者只覆盖已知告警类型，只在报告的对比章节里说明 |

对老师的说法：**底座是开源智能体框架 AgentScope，领域设计借鉴课程给定的 APT-Hunter，属于"基于现有开源系统改造"。**

### 2.3 为什么不直接拿 APT-Hunter 当底座

APT-Hunter 的主体是规则检测工具，智能体是 v4.0 新加的一个模块。这个模块和它的报告格式、网页界面绑在一起，不能单独拿出来对话，也没有给记忆和上下文管理留扩展位置。改它的源码还要处理 GPL-3.0 协议。所以我们借它的设计，不改它的代码。

## 3. 系统架构

```text
用户（终端或网页）
   │ 自然语言提问
   ▼
┌─────────────── AgentScope 2.0（底座，直接使用）───────────────┐
│  ReAct 循环：思考 → 调工具 → 看结果 → 再思考 → 回答            │
│  上下文管理：历史压缩、工具结果截断          （第 4 周接入）   │
│  记忆：跨会话记住结论和误报                  （第 5 周接入）   │
│  中间件：事件编号校验、调用轨迹              （第 6 周接入）   │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用
┌───────────────────────────▼──── 我们新增的日志安全层 ─────────┐
│  系统提示词：日志安全分析员，结论必须引用事件编号              │
│  日志工具（只读）：列案件 / 搜事件 / 取单条事件               │
│                    时间窗上下文 / 统计 / ATT&CK 战术查询      │
│  评测：题目集 + 判分脚本 + 组件开关对比                       │
└───────────────────────────┬──────────────────────────────────┘
                            │ 查询
                  SQLite 日志库（由公开数据集导入）
                  events 事件表 │ cases 案件表 │ labels 标准答案表
```

一次提问的过程：

1. 用户提问。
2. 模型判断需要查什么，调用日志工具。
3. 模型读工具返回的事件。信息不够就继续查。
4. 模型给出回答，并列出支撑结论的事件编号。

两条设计约束：

- **工具全部只读。** 框架自带执行命令、写文件的工具，我们一个都不挂，智能体只能查日志。
- **标准答案对智能体不可见。** 数据集里的文件名和战术标签就是答案，单独存在 `labels` 表里。任何工具都不返回它，只有评测脚本读取。

## 4. 组件设计

每个组件由谁做、哪一周做、怎么验收，见第 6 节。

| 组件 | 做法 | 周次 |
|---|---|---|
| ReAct 循环 | 用 AgentScope 的 `Agent` 和终端对话入口，模型接 `deepseek-flash` | 1–2 |
| 日志工具（3 个基础） | 列出案件概况；在案件里按关键词或事件类型搜索；按事件编号取单条事件 | 2 |
| 日志工具（3 个补齐） | 看某条事件前后一段时间的上下文；按事件类型或主机统计；查询 ATT&CK 战术说明 | 3 |
| 上下文管理 | 配置 `ContextConfig`：对话历史占满多少比例时自动压缩，单次工具结果最长多少 | 4 |
| 记忆 | 接记忆中间件，只记两类内容：已确认的结论、常见误报 | 5 |
| 证据校验 | 写一个中间件，检查回答引用的事件编号是否存在于日志库 | 6 |
| 界面 | 用框架自带的网页界面，或展示每一步的调用轨迹 | 6 |
| 评测 | 题目集加脚本，统计准确率，对比各组件开和关 | 3–7 |

## 5. 输入数据

| 数据 | 来源 | 规模 | 用途 |
|---|---|---|---|
| Windows 攻击日志 | GitHub 仓库 `sbousseaden/EVTX-ATTACK-SAMPLES` 里的 `evtx_data.csv` | 4,633 条事件，来自 249 个日志文件、19 台主机，覆盖 8 种 ATT&CK 战术 | 主数据。每个日志文件当作一个案件，自带战术标签，可直接当评测的标准答案 |
| Linux SSH 登录日志 | GitHub 仓库 `logpai/loghub` 里的 `OpenSSH_2k.log` | 2,000 行，其中 520 行是密码错误的失败登录 | 入门演示。内容直观，适合第一次演示和讲解 |

以上数字是 2026-11-17 下载后统计的。

主数据按战术分的事件数（合计 4,633）：

| 战术 | 事件数 |
|---|---|
| 横向移动 | 1,288 |
| 权限提升 | 1,088 |
| 执行 | 533 |
| 命令与控制 | 432 |
| 防御规避 | 431 |
| 持久化 | 411 |
| 凭据访问 | 283 |
| 发现 | 167 |

选这两份数据的原因：

- 公开可下载，合计不到 5 MB。
- 不需要 Windows 环境和管理员权限。
- 主数据自带标签，评测不用从零标注。

已知局限：主数据全部是攻击样本，没有正常业务日志。所以能评"判断是哪类攻击"，不能评"从大量正常日志里找出攻击"。有余力时可以由 B 补一份正常日志作对照，这一项不进主排期。

## 6. 分工与排期

### 6.1 四个人各自负责什么

| 成员 | 定位 | 负责内容 | 写代码吗 |
|---|---|---|---|
| **A**（大四，人工智能） | 指导与验收 | 定方案；分发模型 API key；每周花 15 分钟检查进度；同学卡住时帮忙排查；最后统稿 | 不写，只看 |
| **B**（大三，网安） | 数据与安全判断 | 读懂数据集；挑选案件；写题目和参考答案；判断智能体答得对不对；整理常见误报；主责评测 | 基本不写，偶尔改题目文件 |
| **C**（大二，计算机） | 循环与工具 | 跑通 ReAct 循环；写日志查询工具；写证据校验；写评测脚本 | 写，用 AI 辅助 |
| **D**（大二，计算机） | 上下文、记忆与界面 | 配置上下文管理；接记忆；做界面展示；汇总对比结果 | 写，用 AI 辅助 |

这样分有三点考虑：

- B 的网安背景用在"判断答得对不对"上，这件事另外两位同学做不了。
- C 和 D 各管一条线，互不等待。
- 每个人每周都有一件能单独验收的事。

### 6.2 每周每个人做什么

| 周 | 本周目标 | B（网安） | C（循环与工具） | D（上下文、记忆、界面） | 验收 |
|---|---|---|---|---|---|
| 1 | 环境和数据就位 | 读数据说明，挑 10 个案件，每个写一句"这里发生了什么" | 装环境，跑通原型的终端对话 | 装环境，运行建库脚本，确认能查到事件 | 三个人的电脑上都能对话；库里有数据 |
| 2 | ReAct 循环跑通 | 用挑好的 10 个案件各问一次，记下答得对不对 | 读懂原型里的循环和 3 个基础工具，能给组里讲清每一步 | 读懂建库脚本和数据表；改一处提示词，观察效果 | 问一个案件的可疑行为，能看到它自己查库再回答 |
| 3 | 工具补齐 | 写 20 道题的初稿：题目、标准战术、关键证据 | 新增"时间窗上下文"和"统计"两个工具 | 新增 ATT&CK 战术查询工具；改提示词，固定回答格式 | 新工具各自能跑；回答带事件编号 |
| 4 | 上下文管理，中期演示 | 审 10 个案件的回答，归纳错误类型 | 准备中期演示：3 个问题的完整流程 | 配置上下文管理，开和关各跑一次并记录 | 长对话不报错；有一张开关对比的小表 |
| 5 | 记忆 | 整理 5–10 条常见误报，作为记忆的内容 | 设计"两次会话"演示：第一次分析，第二次复用 | 接记忆，规定记什么 | 新会话能用上之前的结论 |
| 6 | 证据校验与界面 | 出 5 道"诱导编造"的题，测试校验是否生效 | 写证据校验 | 接网页界面或调用轨迹展示 | 编造的事件编号被标出；界面上能看到每一步 |
| 7 | 评测 | 定稿题目集和判分标准，人工复核结果 | 补全评测脚本，跑各种配置 | 汇总成对比表和图 | 一张完整的对比表 |
| 8 | 结题 | 写报告的数据与评测部分 | 写报告的架构与工具部分，录演示视频 | 写报告的上下文、记忆、界面部分，做 PPT | 报告、PPT、演示视频 |

A 每周做三件事：周初确认本周任务；周末按"验收"一栏检查；记下没完成的项，决定补做还是砍掉。

## 7. 评测

评测回答两个问题：这个智能体分析日志准不准；每个组件各起多大作用。

**题目**：从 249 个案件中选 20–30 个，覆盖 8 种战术。第 3 周先写 20 道，时间允许再补到 30 道。每题让智能体分析一个案件，判断属于哪种 ATT&CK 战术，并给出证据。

**标准答案**：数据集自带的战术标签，加上 B 标注的关键证据事件。

**指标**：

| 指标 | 含义 |
|---|---|
| 战术判断准确率 | 判断的战术和标准答案一致的题数，除以总题数 |
| 证据有效率 | 回答引用的事件编号中，真实存在于日志库的比例 |
| 平均工具调用次数 | 每题调用了几次工具 |
| 平均 token 消耗 | 每题消耗的模型计费单位（token）数量 |

**对比**：

| 对比项 | 想说明什么 |
|---|---|
| 不给工具直接回答，对比 ReAct 循环 | 循环和工具有没有用 |
| 上下文管理开，对比关 | 省了多少 token，准确率有没有变 |
| 记忆开，对比关 | 重复出现的情况能不能答得更快更准 |
| 证据校验开，对比关 | 编造的事件编号被拦下多少 |

题目数量少，结论只能说明趋势。报告里会写明这一点。

## 8. 风险与兜底

| 风险 | 应对 |
|---|---|
| 框架更新快，接口变化 | 锁定 2.0.12 版本，项目期间不升级 |
| 同学的电脑是 Windows，安装出问题 | 第 1 周专门用来装环境；原型代码不用只在 macOS 或 Linux 上能跑的写法。Windows 11 + Python 3.11.5 已实测通过（2026-11-18） |
| 框架默认每次调用工具都要用户确认 | 把日志工具声明为只读并放行 |
| 某一周的组件做不出来 | 各周的组件互相独立，跳过一个不影响其他周 |
| 框架本身跑不通 | 日志工具是普通 Python 函数，不依赖框架。最坏情况下换成一个约百行的手写循环，工具、数据、评测都不用改 |
| 模型费用超出预期 | 跑完整评测前，先用 3 道题估算花费 |
| API key 泄露 | key 只放在本机的 `.env` 文件里，不写进代码，不随代码包分发 |

**最低交付**：即使第 3 周以后全部停滞，第 2 周的成果已经满足老师的两条硬要求（见 1.2）。

## 9. 扩展性

课程任务书提到三个扩展方向。第一项在排期内完成，后两项只在报告里说明做法。

- **本地分析与性能测试**：就是第 7 节的评测，第 7 周完成。
- **多智能体交互**：AgentScope 自带"负责人带成员"式的多智能体协作。可以把现在的单个智能体拆成"分诊"和"取证"两个角色，日志工具不用改。
- **与云平台的接口**：模型本身通过云端 API 调用。AgentScope 还自带服务化部署，可以把智能体包装成网络服务对外提供。

## 11. 和上一版方案的区别

上一版（v0.3）以 APT-Hunter 为底座，再自研一层组件接在它后面。放到团队的实际条件下，它有三个问题：

1. **工时对不上。** v0.3 按约 70 人时排期，并且默认 A 是主程。实际动手的是 B、C、D 三人，合计 24–48 人时，编程基础都不强。
2. **老师的第二条要求没有真正满足。** 旧原型 `apt-agent` 是固定流程，没有"模型自己决定下一步"的循环，也不能对话。v0.3 用 APT-Hunter 自带的分诊智能体来顶，但它是批量分诊，不是对话，同学也没有亲手搭过循环。
3. **依赖太重。** 需要 Windows 管理员权限、自采日志、运行攻击模拟、对接 APT-Hunter 的内部接口，还要处理 GPL 协议隔离。任何一环卡住两周，项目就完不成。

本版的处理：底座换成 AgentScope；数据换成公开数据集；旧原型 `apt-agent` 不再继续开发，只作为设计参考。
