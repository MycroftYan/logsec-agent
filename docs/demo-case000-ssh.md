# 实测记录：case_000 暴力破解溯源（一次撞上限的提问，很有教学价值）

这次提问**没有一次答完**：智能体调用了 28 次工具，撞到 10 轮循环上限才被迫收尾。
留在这里有两个用途：说明第 3 周为什么必须加"统计"工具；说明"模型给的数字必须回查"。
原始终端输出见同目录 [`demo-case000-ssh.log`](demo-case000-ssh.log)。

| 项目 | 内容 |
|---|---|
| 日期 | 2026-11-18 |
| 环境 | Windows 11、Python 3.11.5、AgentScope 2.0.12 |
| 模型 | `deepseek-flash` |
| 命令 | `python ask.py "case_000 里有没有暴力破解的迹象？哪个来源 IP 最活跃？"` |
| 结果 | 28 次工具调用，输入 120,162 / 输出 5,662 token，**结束原因 exceed_max_iters** |

## 它做了什么

前 4 步很正常：搜 `Failed password`、搜 `Invalid user`、看 SSH 案件概况、搜 `Accepted`。到这里就能确定
"有大量失败登录、只有 1 条成功登录"。

问题出在第 7 步之后：为了回答"哪个 IP 最活跃"，它没有聚合统计能力，只能一个地址一个地址地
`search_events(keyword=IP)`，再把 `Failed password` 一页页翻（offset 60/120/180/260/300/340/440/480/858……）。
28 次调用里有 20 次都花在这件事上。

## 它的答案，以及答案里哪里要打问号

它给出的结论（原文摘录）：

> case_000 是典型的 SSH 暴力破解：`Failed password` 520 条、`Invalid user` 113 条、`BREAK-IN ATTEMPT` 85 条。
> 最活跃的源是 **183.62.140.253**，命中 867 条相关日志（`867 > 187.141.143.180 的 349`）。
> 全案只有 1 条登录成功（`fztu` from 119.137.62.142），且该地址没有任何失败尝试，更像是合法登录，
> **没有证据显示爆破成功**。

我们用 SQL 逐条核对（`case_000`，2,000 条事件）：

| 模型的说法 | 回查结果 | 判定 |
|---|---|---|
| 失败口令 520 条 | `summary LIKE '%Failed password%'` = **520** | ✅ 对 |
| 登录成功 1 条（fztu / 119.137.62.142） | `Accepted` = **1**，且该 IP 无失败记录 | ✅ 对 |
| 最活跃源 183.62.140.253 | 提到该 IP 的日志行 = **867** 条 | ✅ 数字真实 |
| "867 条相关日志"≈最活跃的判断 | 该 IP 的 **失败口令实际是 286 次**；867 里还包含 `Invalid user`、`BREAK-IN`、`disconnect` 等行 | ⚠️ **口径不对** |
| `Invalid user` 113 条 | 含 `Invalid user` 的事件是 **365** 条（113 可能是"不同用户名"数） | ⚠️ 口径待确认 |

"哪个 IP 最活跃"这个判断本身没错（183.62.140.253 在失败口令上也是第一，286 > 80 > 46 > 26），
但**它给的数字是"日志行命中数"，不是"爆破次数"**。模型自己也注意到了，主动写了局限：

> "867 条是多类日志行合计，不能直接当作 867 次口令尝试"；"未对全部 520 条失败记录逐条做 IP 聚合，若需精确排名建议再做一次全量分组统计"。

这正是评测要量化的东西：**"证据有效率"要看的不是"数字看起来像不像真的"，而是"这个数字能不能用一条确定的查询复现"**。

## 结论：第 3 周要补的工具就是治这个

| 现在的问题 | 第 3 周怎么解决 |
|---|---|
| 没有统计工具，只能一页页翻搜索结果 → 28 次调用、12 万 token | 加 `count_events(by="ip")`，一个调用直接出 `IP → 次数` 排名 |
| 关键词命中数 ≠ 业务计数（867 vs 286） | 同上：按 `EventID`/`Failed password` 等条件分组计数，口径写死在工具里 |
| 不知道事件前后发生了什么，只能挨个查 | 加 `get_event_context(uid, window_seconds=60)` |
| 判断战术靠模型自己回忆 | 加 `lookup_tactic(tactic)`，给中文说明和典型日志迹象 |

改造之后重跑同一个问题，工具调用次数应该从 28 次降到 5 次以内，答案里的数字也都会是数据库聚合出来的。
这就是第 7 周"组件开关对比"里的一张表。
